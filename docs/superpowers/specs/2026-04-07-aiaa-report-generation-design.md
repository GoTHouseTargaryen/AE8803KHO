# AIAA Report Generation — Design Specification

**Course:** AE 8803 KHO — Space Logistics and Optimization (Prof. Koki Ho)
**Deadline:** April 20, 2026
**Feature:** Auto-compiled LaTeX/PDF AIAA report with simulation results injection

---

## 1. Overview

A modular LaTeX report system that produces a publication-quality AIAA conference paper for the in-space assembly mission planning project. Pre-written static sections cover the full scientific content (introduction, approach with equations, system description, conclusion). A dynamically generated Results & Discussion section is compiled from simulation runs the user tags in the GUI. A single "Compile Report" button in the web frontend triggers the backend to generate matplotlib pgf figures, render the results section, run `pdflatex`, and return a downloadable PDF.

## 5. Section Content

### 5.1 Abstract
~150 words. Static text. Summarizes the problem (in-space assembly at L4), the DP approach, and the simulation tool. Contains placeholder bracketed values (e.g. `[X launches]`, `[Y weeks]`) that the user fills in manually after reviewing their tagged results — the abstract is not auto-generated.

### 5.2 Introduction
- Motivation for kilometer-scale spacecraft (deep-space missions, space solar power, large aperture telescopes)
- Earth-Sun L4 rationale: gravitational stability (co-rotating with Earth), continuous solar power, distance from debris belts
- Challenge statement: multi-year assembly campaign, multi-nation vehicle fleet, crew rotation logistics, on-orbit sequencing under uncertainty
- Paper contributions: (1) DP formulation over time-expanded network, (2) multi-objective optimization with beam search, (3) interactive simulation tool with real-time playback

### 5.3 Approach
All mathematical formulation. Subsections:

#### 5.3.1 Time-Expanded Network & DP Formulation

State vector at epoch $t$:
$$S(t) = \bigl\{\mathcal{M}(t),\ \mathcal{C}(t),\ \mathcal{Q}(t),\ n_{\mathrm{tugs}}(t)\bigr\}$$

where $\mathcal{M}(t)$ is the set of completed modules, $\mathcal{C}(t)$ is the set of docked crew vehicles with remaining rotation periods, $\mathcal{Q}(t)$ is the cargo-in-transit queue, and $n_{\mathrm{tugs}}(t)$ is the count of reusable tugs available at LEO.

Decision variables at epoch $t$:
$$D(t) = \bigl\{\text{launches},\ \text{crew allocation},\ \text{assembly tasks},\ \text{tug assignments}\bigr\}$$

Bellman optimality equation:
$$V(S,t) = \min_{D \in \mathcal{D}(S,t)} \bigl[\, c(S, D, t) + V(S', t+1) \,\bigr]$$

#### 5.3.2 Multi-Objective Cost Function

Normalized weighted sum of three objectives:
$$J = w_1 \frac{N_{\mathrm{launches}}}{N_{\mathrm{launches}}^{\max}} + w_2 \frac{T}{T^{\max}} + w_3 \frac{C}{C^{\max}}$$

with safe normalization $f(x, x^{\max}) = x / x^{\max}$ (returns 0 if $x^{\max} = 0$). Weights $w_1, w_2, w_3 \geq 0$ are user-adjustable in the GUI. Upper bounds are set as $N_{\mathrm{launches}}^{\max} = 2|\mathcal{M}_{\mathrm{total}}|$, $T^{\max} = T_{\mathrm{horizon}}$, $C^{\max} = 2000|\mathcal{M}_{\mathrm{total}}|$ M\$.

#### 5.3.3 Transfer Model

Payload delivered to L4 via the Tsiolkovsky rocket equation:
$$m_{\mathrm{delivered}} = m_{\mathrm{LEO}} \cdot \exp\!\left(\!\frac{-\Delta v}{I_{sp}\, g_0}\right)$$

where $g_0 = 9.80665 \times 10^{-3}\ \mathrm{km/s^2}$. Two transfer options are modeled:

| Type | $\Delta v$ (km/s) | Transit (days) |
|---|---|---|
| Direct (Hohmann-like) | 4.1 | 60 |
| Low-energy (WSB) | 3.8 | 120 |

For LEO-only vehicles requiring a transfer stage of dry mass $m_d$ and propellant mass $m_p$, the maximum deliverable cargo is constrained by the tug's mass ratio:
$$m_{\mathrm{cargo,max}} = \frac{R\,m_d - (m_d + m_p)}{1 - R}, \qquad R = \exp\!\left(\!\frac{\Delta v}{I_{sp}\,g_0}\right)$$
$$m_{\mathrm{delivered}} = \min\!\left(m_{\mathrm{payload}},\ m_{\mathrm{cargo,max}}\right)$$

#### 5.3.4 Crew Model

Total crew forms a single pool across all docked vehicles:
$$n_{\mathrm{crew}} = \sum_{v \in \mathcal{C}(t)} n_v$$

EVA pair and IVA support allocation solved iteratively for stable configuration:
$$n_{\mathrm{IVA}} = \left\lceil \frac{n_{\mathrm{EVA\,pairs}}}{k_{\mathrm{IVA}}} \right\rceil, \qquad n_{\mathrm{EVA\,pairs}} = \left\lfloor \frac{n_{\mathrm{crew}} - n_{\mathrm{IVA}}}{2} \right\rfloor$$

where $k_{\mathrm{IVA}}$ is the maximum EVA pairs per IVA monitor (default: 2). EVA productive hours per period with duty cycle $\eta_d$ (default: 0.6):
$$H_{\mathrm{EVA}} = n_{\mathrm{EVA\,pairs}} \cdot h_{\mathrm{session}} \cdot d_{\mathrm{period}} \cdot \eta_d$$

Robotic arm hours (24/7 operation, time penalty $\eta_r$ relative to crew EVA):
$$H_{\mathrm{robotic}} = \frac{n_{\mathrm{arms}} \cdot h_{\mathrm{period}}}{\eta_r}$$

Crew/cargo trade-off per vehicle:
$$m_{\mathrm{cargo}} = m_{\mathrm{capacity}} - n_{\mathrm{crew}} \cdot m_{\mathrm{per\,crew}}$$

#### 5.3.5 Proximity & Congestion Model

Scale-adaptive congestion penalty applied to effective assembly hours each period:
$$\pi(n, p) = 1 + \frac{\alpha\,(n-1)^{\beta}}{C(p)}, \qquad C(p) = C_{\mathrm{base}} + (C_{\mathrm{max}} - C_{\mathrm{base}})\,p$$

where $n$ is the number of vehicles in proximity, $p = |\mathcal{M}_{\mathrm{built}}| / |\mathcal{M}_{\mathrm{total}}|$ is build progress, and default parameters are $\alpha = 0.1$, $\beta = 1.5$, $C_{\mathrm{base}} = 2$, $C_{\mathrm{max}} = 10$. Effective hours available for assembly:
$$H_{\mathrm{EVA,eff}} = \frac{H_{\mathrm{EVA}}}{\pi(n,p)}, \qquad H_{\mathrm{robotic,eff}} = \frac{H_{\mathrm{robotic}}}{\pi(n,p)}$$

Cumulative collision risk accumulated over all periods:
$$\mathcal{R} = \sum_{t=0}^{T} \kappa \cdot \binom{n(t)}{2} \cdot \Delta t$$

#### 5.3.6 Partial Assembly (Work-in-Progress)

Modules requiring more hours than available in one period are tracked as WIP with remaining hours $h_r$. Updated each period:
$$h_r^{(t+1)} = \max\!\left(0,\ h_r^{(t)} - \min\!\left(h_r^{(t)},\ H_{\mathrm{available}}^{(t)}\right)\right)$$

Module $m$ is marked complete when $h_r \leq \varepsilon$ (default $\varepsilon = 0.01\ \mathrm{h}$).

#### 5.3.7 Pad Turnaround Constraint

Launch vehicle $v$ is only eligible for launch if sufficient periods have elapsed since its last use:
$$t - t_{\mathrm{last}}(v) \geq \Delta t_{\mathrm{pad}}, \qquad \forall\, v \in \mathcal{V}_{\mathrm{cargo}} \cup \mathcal{V}_{\mathrm{crew}}$$

Default pad turnaround: $\Delta t_{\mathrm{pad}} = 2$ periods (14 days).

#### 5.3.8 Beam Search Pruning

State space explosion (up to $2^{50}$ states for a 50-module spacecraft) is mitigated by forward DP with beam search. At each epoch, the top-$K$ states are retained by a progress heuristic $\phi$:
$$\phi(S) = 10\,|\mathcal{M}_{\mathrm{built}}| + 3\,|\mathcal{D} \setminus \mathcal{M}_{\mathrm{built}}| + |\mathcal{Q}| + \bigl(5 + 3r\bigr)\cdot\mathbf{1}[n_{\mathrm{crew}}>0] + 0.5\,|\mathcal{W}|$$

where $r = |\mathrm{available}(\mathcal{M}_{\mathrm{built}}) \cap \mathcal{D}|$ is the count of modules ready to assemble, $\mathcal{Q}$ is cargo in transit, and $\mathcal{W}$ is the current WIP set. Default beam width: $K = 100$.

### 5.4 System Description
- Architecture overview: Python simulation core (Flask REST API) + Next.js GUI
- Module catalog: 14 module types across 6 subsystem categories
- Assembly DAG: parametric generator produces topologically valid dependency graph
- Vehicle catalog: 9 cargo vehicles, 4 crew vehicles, 3 transfer stages (from Artemis Accords nations)
- One figure: system architecture diagram (static, in `figures/`)
- One table: vehicle catalog summary

### 5.5 Results & Discussion
Fully generated from the Jinja2 `results.tex` template. Structure:
- One subsection per tagged run: scenario parameters table, Gantt chart, resource utilization chart, cost breakdown chart, modules-completed-over-time chart, key metrics table (total launches, periods, cost, cumulative risk)
- Final subsection: Pareto frontier analysis across tagged runs (if ≥2 runs tagged)
- Discussion text is templated: the template emits fixed comparative sentences populated with actual metric values (e.g. "Run A completed assembly in \VAR{periods} periods using \VAR{launches} launches at a total cost of \$\VAR{cost}M."). No free-form AI generation — all prose is pre-written template text with variable substitution.

### 5.6 Conclusion
- Summary of DP formulation and tool capabilities
- Key findings from reference scenarios
- Limitations: beam search approximation (not globally optimal), simplified delta-v model (no full ephemeris), deterministic assembly (no failure modes)
- Future work: higher-fidelity orbital mechanics, multi-site assembly, refueling depots, stochastic assembly duration

## 6. Backend: `/api/report` Endpoint

**Method:** `POST`  
**Location:** `simulation/app.py`

### Request Schema
```json
{
  "runs": [
    {
      "label": "Baseline — Chemical/Solar 0.5 km",
      "config": {
        "spacecraft": { "length_km": 0.5, "structure_type": "truss",
                        "propulsion_type": "Chemical", "power_type": "Solar" },
        "cargo_vehicles": ["Starship"],
        "crew_vehicles": ["Crew Dragon"],
        "transfer_stages": ["Chemical Kick Stage"],
        "weights": { "w_launches": 1.0, "w_time": 1.0, "w_cost": 1.0 },
        "proximity": { "alpha": 0.1, "beta": 1.5,
                       "base_capacity": 2.0, "max_capacity": 10.0 },
        "period_days": 7,
        "beam_width": 100,
        "max_periods": 200
      },
      "result": {
        "total_launches": 3,
        "total_periods": 45,
        "total_cost_million": 350.0,
        "modules_completed": 16,
        "cumulative_risk": 0.0023,
        "timeline": [ ... ]
      }
    }
  ]
}
```

### Response
`Content-Type: application/pdf` — binary PDF stream.

### Server-Side Steps
1. Create `report/generated/` if not exists; clear stale pgf files
2. For each run `i`:
   - Parse timeline into period-indexed action lists
   - Generate `run_{i}_gantt.pgf` — Gantt chart (matplotlib pgf backend)
   - Generate `run_{i}_resources.pgf` — crew count + vehicle count over time (dual-axis)
   - Generate `run_{i}_cost.pgf` — cost breakdown by vehicle (horizontal bar)
   - Generate `run_{i}_modules.pgf` — modules completed over time (step chart)
3. If ≥2 runs: generate `pareto.pgf` — scatter of (total_launches, total_periods, total_cost) across runs
4. Render `report/sections/results.tex` from Jinja2 template using all runs data
5. Run `pdflatex` twice via `subprocess.run` with `cwd` set to the `report/` directory and `-interaction=nonstopmode report.tex`; using `cwd` avoids Windows path separator issues and ensures all `\input{}` relative paths resolve correctly
6. Read `report/report.pdf` and stream as response with `Content-Disposition: attachment; filename="report.pdf"`; return HTTP 500 with last 50 lines of `report.log` on compilation failure

### Error Handling
- `pdflatex` not found → HTTP 503 with message "LaTeX not installed"
- Compilation failure → HTTP 500 with last 50 lines of `report.log`
- No runs provided → HTTP 400

## 7. Chart Specifications (matplotlib pgf backend)

All figures use `matplotlib.use('pgf')` with rcParams matching AIAA font stack:
```python
matplotlib.rcParams.update({
    "pgf.texsystem": "pdflatex",
    "font.family": "serif",
    "text.usetex": True,
    "pgf.rcfonts": False,
})
```

| Figure | Type | X-axis | Y-axis | Notes |
|---|---|---|---|---|
| Gantt | Broken H-bar | Period number | Module/vehicle | Color by action type |
| Resources | Line (dual-axis) | Period | Crew count / vehicle count | Left=crew, right=vehicles |
| Cost | Horizontal bar | Cost ($M) | Vehicle name | Breakdown by vehicle/category within the run |
| Modules | Step | Period | Modules completed | Annotate completion |
| Pareto | Scatter | Total launches | Total periods | Color = total cost |

Figure size: 3.5 inches wide (single AIAA column), height proportional. All text at 9pt to match body.

### New TypeScript types

```typescript
  id: string                     // uuid generated at tag time — stable key
  label: string                  // user-editable display name
  config: SimulationRequest
  result: SimulationResult
  taggedAt: string               // ISO timestamp
}

interface ReportRequest {
  runs: TaggedRun[]
}
```

### New components
- **`TagRunButton.tsx`** — toggle button rendered in `MetricsSummary.tsx` after a simulation completes. Clicking opens a small inline text field to set the run label, then adds to `taggedRuns`.
- **`TaggedRunsSidebar.tsx`** — collapsible panel listing tagged runs with editable labels and ✕ remove buttons. Renders in `Dashboard.tsx`.
- **`CompileReportButton.tsx`** — primary button in Dashboard header. Disabled when `taggedRuns.length === 0`. On click: POSTs to `/api/report`, streams response, creates blob URL, triggers browser download.

### New API function (api.ts)
```typescript
export async function compileReport(runs: TaggedRun[]): Promise<Blob> {
  const resp = await fetch(`${API_BASE}/api/report`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ runs }),
  })
  if (!resp.ok) throw new Error(await resp.text())
  return resp.blob()
}
```

## 11. Scope Boundaries

**In scope:**
- All static `.tex` section files fully written with real content
- `results.tex` Jinja2 template generating one subsection per tagged run
- All five matplotlib pgf chart types
- `/api/report` Flask endpoint
- Three new React components + Zustand store additions
- `aiaa.cls` class file (download from AIAA or use compatible open version)

**Out of scope:**
- Re-running the simulation from the report endpoint (report uses already-computed results)
- Cloud/server deployment of pdflatex
- Word/DOCX export
- Automated abstract generation from results (abstract is static)
